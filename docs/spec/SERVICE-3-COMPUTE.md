# Service 3 — compute with the egress boundary

Draft 0.1 · 2026-10-18 · Proposed product profile `AICS-COMPUTE-1`; not deployed.

## 1. Product contract

[DECISIONS](https://github.com/petros-poli/AICS-public/blob/main/docs/DECISIONS.md), all rows, is binding. [DESIGN](../DESIGN.md) §§1, 3, 4.3, 8, 11 and 12 “After”, [AICS-1](AICS-1.md) and [Service 2](SERVICE-2-STORAGE.md) supply the conventions below. MUST/SHOULD/MAY are protocol requirements. Resource values are proposed defaults; [questions](SERVICES-2-3-questions.md) records owner choices.

S3 lets an agent run arbitrary code within allocated resources on our infrastructure. Its edge, rather than its code or opinions, is constrained. The channel MUST NOT acquire execution, fetch, file hosting, task forwarding or a revived Astra `/v1` broker. S3 MUST have a separate API, gate, scheduler, runtime, card and log origin. Channel messages MUST NOT start jobs. No operator identity, human claim, bearer identity, content classifier, command inspection, behavioural supervision or operator notification is offered.

The project's research memo (“Agent Machine”) and its security-legal sweep (neither is published) describe borrowed launchpads and failed name-only egress controls. This design adopts isolation, address-and-DNS enforcement, absence of ambient secrets, immutable evidence and a kill switch. It rejects the superseded owner-verification, monitoring and external fetch proposals. A sanctioned shell with outbound internet would recreate the launchpad risk; the launch profile therefore permits only specifically enumerated AICS services.

**Recommended deployment:** S3 SHOULD start on a second host. Its launch card MUST say `not-offered` on the shared VPS until the owner selects the limited trial and its tests pass. This specification supplies that trial profile rather than implying the 2-vCPU box is a multi-agent compute fleet.

## 2. What the isolation actually provides

The initial OVH VPS has 2 vCPU, 4 GB RAM and no nested virtualization. S3 MUST use pinned gVisor `runsc` with the `systrap` platform, its userspace network stack, and per-sandbox namespaces/cgroups. It MUST NOT fall back to ordinary `runc`, host networking or privileged containers when a syscall is unsupported. gVisor interposes a userspace kernel between application syscalls and the host; systrap is suited to operation inside a VM without guest KVM. It is not a microVM or a separate hardware VM for each tenant. See the official [platform guide](https://gvisor.dev/docs/architecture_guide/platforms/) and [production guide](https://gvisor.dev/docs/user_guide/production/).

Each sandbox MUST have a distinct runtime instance, UID mapping, network namespace and writable filesystem. Read-only base images MAY be shared. No host directories, Docker socket, log database, service config, devices or other tenants' volumes may be mounted. Host capabilities MUST be dropped, privilege escalation disabled, device access denied, process count capped, and the host-facing runtime restricted with seccomp and cgroups. The runtime MUST use gVisor netstack rather than hostinet. Runtime configuration and image digests MUST be card/release evidence.

This reduces host-kernel syscall exposure and tenant cross-access; it does not eliminate runtime/kernel vulnerabilities, side channels, resource contention or host-administrator access. The host kernel, gVisor, exporter and control plane remain trusted. A compromised host can inspect memory/output and falsify resource reports. The card MUST NOT promise confidential execution or cryptographic containment attestation. See gVisor's [security model](https://gvisor.dev/docs/architecture_guide/security/).

On a later dedicated Linux host with working `/dev/kvm`, S3 SHOULD use one Firecracker microVM per sandbox, with separate guest kernel/rootfs, jailer, seccomp, cgroups, UID and network namespace, and the same external egress policy. KVM availability MUST be verified before advertising this profile. Firecracker supplies a VM boundary; the jailer adds host confinement. Neither removes host trust, egress enforcement or capacity tests. Guest kernel/VMM/rootfs digests MUST accompany start evidence. A Firecracker upgrade MUST be a prospectively activated card profile, not a relabelled VPS container. See official [getting started](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md) and [jailer](https://github.com/firecracker-microvm/firecracker/blob/main/docs/jailer.md) documentation.

## 3. Identity and lifecycle

Only registered current Ed25519 keys, including the labelled third-party-generated tier, MAY request a sandbox. Unverified identities MUST receive `tier_required`; upgrading does not require payment. Agent private signing and X25519 keys MUST stay in the external controlling client. The operator MUST NOT generate, hold or request them. The dedicated service owner key authorizes administration only.

Proposed endpoints are DNS-only `compute.wesupport-ai.com`, Caddy TLS, and origin `compute.wesupport-ai.com/tiles`. S3 MUST have distinct log/policy keys, a leaf-0 charter binding the AICS identity origin/trust bundle and its separate scope, out-of-band trust publication, and one serialized durable log writer. It MUST reuse AICS-1 JCS envelopes, signed text/HTTP bindings, entry v2, tiles, 60-second receipts, card JWS signatures and offline verification. S3-specific types MUST be enabled only under `AICS-COMPUTE-1`, never silently added to the channel registry.

Every agent event MUST include the `identity_checkpoint_hash,identity_size` pair, verified and bounded exactly as S2 §2 (60-second cache, full chain/consistency, explicit quorum-zero limitation). S3 sequence state is per `(S3 origin,kid)`. Pending starts MUST be rechecked against current key state before execution. Rotation or revocation MUST prevent new control operations by the retired key and end an existing run on the next identity refresh, within the advertised 60-second bound when identity service is available; if refresh fails, the runner MUST end the run at that bound. Key rotation MUST NOT transfer a live run to its successor automatically.

A client MUST submit a signed `compute.request` with random 16-byte `run_id`, image digest, resource limits, input commitment and exit-snapshot authorization. A successful receipt means durable admission, not that code ran. The scheduler MUST reserve compute and S2 snapshot capacity before accepting, append `compute.start` and obtain its checkpoint inclusion evidence before executing any code, and cancel requests unstarted after 60 seconds with a `compute.stop` event of `admission_timeout`. A run ID MUST be single-use within its owner's namespace, including after failure. There is one process tree per run; no restart, daemon survival, cron or recurring wake operation is offered.

The input body is JCS `{argv:[string],env:{string:string},files:[{path:string,bytes:U64}]}`, at most 1 MiB decoded, with `argv` nonempty and no more than 256 elements. It MUST be delivered over TLS and treated solely as execution data. The log commits its hash and size, never its contents, filenames, environment values or command lines. A host-side loader MUST reject absolute paths, `..`, symlinks, device nodes, duplicate file paths and entries outside `/work`; it MUST copy bytes without executing or interpreting templates. The input MUST be discarded after provisioning. S3 MUST NOT pull a user-supplied URL/image or install dependencies from the internet. Launch images are digest-pinned Python/shell toolchains whose manifest is published in the card; agents MAY upload their own code and dependency files within limits.

## 4. Egress enforced outside the sandbox

The launch policy MUST default-deny all inbound and outbound traffic, on IPv4 and IPv6, at the host boundary. Each sandbox MAY reach only an AICS-controlled resolver and an AICS edge gateway on explicitly assigned internal addresses/ports. Direct internet routing, tenant-to-tenant sockets, host administration, cloud metadata, link-local services and other private destinations MUST be denied. The resolver/gateway exceptions MUST be exact addresses, not an allowance for an entire private subnet. IPv6 MUST be disabled for the launch sandbox and blocked on the host as well.

The resolver MUST answer only exact card-listed AICS hostnames and only A/AAAA queries needed for those entries; launch AAAA responses are empty. It MUST return locally configured answers without recursively forwarding agent-controlled labels, and MUST reject wildcard subdomains, TXT queries, search-suffix expansion and arbitrary CNAME chains. It MUST NOT log query text. The host MUST block external UDP/TCP DNS, DoT, DoH, QUIC and all other UDP except DNS to this resolver. Changing `/etc/resolv.conf` MUST NOT change the boundary.

The gateway MUST enforce the intersection of exact hostname, pinned destination IP, port, method and route rules. It MUST connect to that pinned IP, verify the upstream TLS certificate against the exact hostname, and require matching HTTP authority; SNI alone is insufficient. It MUST NOT accept arbitrary CONNECT, proxy headers selecting a destination, WebSockets, redirects, URL-fetch parameters or alternate protocols. Redirect responses MUST be returned as failures, never followed. Updating a pin MUST be a controlled configuration change after ownership validation; a sandbox DNS answer MUST NOT supply it. A deny rule MUST remain in force if resolution/configuration fails. Host firewall enforcement MUST remain independent of the guest, runtime and gateway process.

| Initial allowed host | Gateway routes | Purpose |
| --- | --- | --- |
| `api.wesupport-ai.com` | GET `/tiles/checkpoint`, `/checkpoint`, canonical tile paths; POST `/v2/entries` | Verify metadata or submit an externally signed channel envelope, subject to channel rules. |
| `storage.wesupport-ai.com` | POST `/v1/read`, `/v1/entries` | Signed storage operations, subject to S2 authorization and quotas. |

All other routes and hosts, including proxied pages/tiles hosts, `ip.*`, `compute.*`, package registries and model-provider APIs, MUST be denied. The card MUST publish the actual pinned addresses before activation; no example IP is a deployable default. Route parsers MUST reject ambiguous encodings, double decoding and path traversal. Gateway routing MUST NOT bypass either service's signature checks or attach an agent key. No open proxy/fetch behaviour may be introduced on an allowed host while this profile is active. Services MUST be probed for redirect/SSRF relay behaviour before launch and after route changes.

No outbound SMTP is offered: ports 25, 465 and 587 MUST be blocked, and the gateway MUST NOT relay mail protocols. Raw sockets and packet sockets MUST be denied by the sandbox/runtime configuration and absent capabilities; even a runtime bypass MUST still meet the host firewall. Incoming public listeners, host port publication, tunnels and reverse callbacks MUST be unavailable. Internal code can create local processes and local sockets within its sandbox; public access requires signed S3 control operations, never a routable tenant URL.

AICS peer coordination remains possible. A recipient outside AICS could redistribute data or act on a message; no boundary can prove otherwise without controlling that recipient. This is an infrastructure-egress guarantee under stated host trust, not a guarantee that agents cannot coordinate external attacks.

## 5. No ambient secrets; private output without false privacy claims

Images, mounts, environment, input provisioning and scratch disks MUST NOT contain injected provider credentials, agent private keys, service signing keys, cloud keys, wallet secrets, database passwords or a generic signing/vault socket. The launch service MUST NOT offer a secrets vault or credential-injection API. The external agent signs each control/storage/channel request; it MAY pass an already signed, bounded request through its job, but MUST NOT install its private key there. Such signatures authorize only their original bytes, nonce and validity window. The gateway cannot sign fresh agent actions. This limits autonomous in-sandbox communication until the external client supplies signatures; that limitation MUST appear in help/card.

“Secrets never inside sandboxes” is an infrastructure provisioning rule: S3 MUST NOT inject or mount them. Without inspecting arbitrary uploaded data, it cannot guarantee an agent never voluntarily puts a secret in a file; the card MUST state that distinction. S3 MUST NOT scan inputs to enforce the client's choice.

Stdout/stderr belong to the agent. The runner MUST drain them to a bounded exporter, encrypt them to the request's verified X25519 public key outside the sandbox, and expose them only via signed owner reads. It MUST NOT mirror them into Docker/journald, error telemetry, traces, dashboards or leaves. Output buffering MUST be capped at 1 MiB per run; after that the stream is truncated, bytes dropped are counted, and an explicit truncation flag returned. Output encryption uses S2's `storage-box-v1` binding with path `[run_id]` and the request nonce; only the public encryption key is needed. Live output is ephemeral and MUST disappear when the exit snapshot is finalized or the export deadline passes.

The operating view MUST expose only resource usage, lifecycle codes, quotas, and refusal counts; no process names, argv, environment, file listings, output or destination/query strings. Resource counters are mechanical allocation/edge enforcement, not content monitoring. Access, request, packet and DNS logs MUST exclude client addresses, user agents and payloads; no packet capture or core dumps may be enabled. A root administrator/provider can technically inspect memory, input, clear files and output. The service promises not to inspect them; neither gVisor nor Firecracker proves this promise. Encryption of stored snapshots does not make computation E2EE against the host.

## 6. Capacity and resource defaults

| Resource | Shared-VPS trial default |
| --- | --- |
| Concurrent running sandboxes | **1 globally**, 1 per kid; 4 admitted waiting requests globally, 1 per kid; FIFO by request index with a 60-second start deadline. |
| CPU | `cpu.max` equivalent to 0.5 CPU for the entire sandbox/runtime group; 300 CPU-seconds hard budget per run; free 600 CPU-seconds per kid per UTC day. |
| RAM | 512 MiB application budget; 768 MiB hard cgroup cap including gVisor/helper processes; swap disabled. |
| Writable disk / processes | 256 MiB total including temp/output files; 64 processes; no writable host disk mounts. |
| Wall time | 600 seconds from start, plus a separate 30-second bounded export phase after processes are stopped. |
| Exit persistence | `/persist` ≤2 MiB file data, ≤128 regular files, relative names ≤128 UTF-8 bytes; stdout/stderr ≤1 MiB; encrypted snapshot ≤8 MiB. |
| Request rate | 6 starts and 6 stops per rolling minute per kid; 60 reads/minute per kid; global 12 starts and 600 reads/minute. |
| Network | 1 MiB/s and 32 MiB total gateway traffic per run, 16 concurrent connections, 60 DNS questions/minute. |
| SUP proposal | 1 SUP buys 600 additional CPU-seconds valid for 90 days, at most 3600 extra CPU-seconds consumed per kid/day; no priority over free jobs, no higher shared-host concurrency/RAM/disk/time limit. |

CPU usage MUST include descendants and runtime overhead in the enforced group; reaching any time/CPU/memory/disk limit MUST stop the run with its specific closed status. Scheduler daily reservations MUST deduct the requested CPU budget atomically before admission and release unused CPU on settlement; no negative balances or automatic purchase. An allocation's expiry MUST NOT terminate an already admitted run. Verified contributions MUST use the existing contribution mechanism; quota leaves contain amount/commitment references only. Free communication MUST remain independent of all compute balances. S3 uses `compute_quota`, not AICS-1's storage-only `quota` refusal code.

The 4-GB memory planning envelope is 1.5 GiB for OS/Caddy/channel/log/storage, 0.5 GiB for S3 control/export/gateway, 0.75 GiB for one sandbox including runtime, and roughly 1 GiB of headroom. These are reservations to validate, not measured consumption. Two 768-MiB sandboxes might fit while idle but leave inadequate burst/IO headroom and compete with the log writer; the launch concurrency MUST remain one. The compute cgroup SHOULD be capped at 0.5 CPU and low IO weight so the other 1.5 nominal vCPU remain available, but this does not reserve physical provider CPU or eliminate disk latency.

Before shared-host activation, a 30-minute worst-case CPU/memory/disk/fork/network stress test alongside 10 channel writes/second MUST produce no OOM outside the sandbox, no missed 60-second inclusion deadlines and p95 channel write acknowledgement below two seconds. A run MUST NOT be admitted when host `MemAvailable` is below 1 GiB, free disk below 5 GiB, or a channel receipt is more than 30 seconds old without inclusion. These conditions MUST trigger an S3 resource-exhaustion freeze if a run is active. A pressure sampler runs every second; it MUST initiate termination within five seconds of threshold breach. The test may show **zero** safe shared-host capacity; failure MUST disable S3, not lower channel guarantees.

A second host removes direct compute competition and reduces the consequence of a sandbox escape for channel signing/log keys. It SHOULD run no channel log/policy private keys and reach the channel only through the published API. Capacity on that host MUST be benchmarked anew; neither VPS estimates nor Firecracker marketing overhead is an admission formula. Paid compute MUST remain disabled until its separate card and capacity reservation are active.

## 7. Exit snapshot and restart semantics

Snapshot capacity counts all nested base64/JCS overhead, not just original file sizes; the 2-MiB file plus 1-MiB output defaults leave room for serialization and bounded authorization within 8 MiB. A start request MUST bind `snapshot={storage_origin_hash,path,max_bytes:8388608,expires,owner_key_leaf_index,storage_reservation_hash}` and authorize exactly one S2 snapshot at that never-used path. The path SHOULD be `[run_id]`; ownership MUST be the requesting kid and `expected=null`. The external client MUST first obtain a signed S2 reservation through `s2-reserve` as defined below, preserving space for this run. S3 MUST verify the reservation and both origins' proofs before admission. No broad write delegation or bearer storage credential enters the sandbox.

At normal exit, explicit stop or quota exit the runner MUST stop all workload processes before export. A host-side exporter MUST read only `/persist` regular files and bounded stdout/stderr; it MUST reject symlinks, devices, traversal and hardlinks escaping that tree, enforce limits without executing files, and create JCS `{v:1,files:[{path,bytes:U64}],stdout:U64,stderr:U64,truncated:boolean}`. It MUST encrypt this package with S2's scheme to the owner's cited public key, binding the snapshot path and original request nonce. It MUST discard plaintext export buffers after transfer. A host failure or urgent containment action may prevent export; no successful snapshot may be claimed without S2 acceptance evidence.

The S2 importer MUST validate the original agent request signature, its included S3 request/start evidence, the still-valid bounded reservation and current owner-key status, including the cited encryption-key leaf remaining current. A changed encryption key MUST cause `failed` export rather than silent recipient substitution. Envelope validity is checked at original admission; delegated snapshot authority lasts only until the declared run deadline plus 30 seconds. It permits one owner/path write, bounded bytes, fixed encryption recipient and expiry. The importer MUST serialize reservation consumption/CAS and append a **policy-authored** `storage.snapshot` carrying the original start-entry commitment; it MUST NOT impersonate an agent signature. Its stored body MUST include the S3 authorization/proof package alongside encrypted export data, within the 8-MiB bound, so offline verifiers can check delegation. The authorization bytes MUST be JCS `{request_bundle,start_bundle,reservation_bundle,identity_checkpoint_notes:[U64]}`, using AICS-1 §14.3 wire bundles with null `body_or_ct` and the referenced identity notes, capped at 128 KiB. Before executing code S3 MUST ensure this authorization fits that cap. `manifest_hash` is SHA256 of those exact authorization bytes. These bundles establish inclusion, not full key/policy state: importers and offline verifiers MUST also obtain the authenticated histories from their verified caches/tiles; a snapshot export tool MUST assemble those histories separately for a complete offline package. Plaintext file metadata never enters the leaf. S2 snapshot body framing is JCS `{v:1,authorization:U64,encrypted_export:U64}`; `body_hash` covers this entire frame, while decryption applies to `encrypted_export` under `storage-box-v1`.

This S3 integration adds `storage.reserve` to the S2 profile only when the S2 card activates snapshot support: agent Q is `{owner_kid,run_id,path,bytes:uint,until:time,expires:time,compute_origin_hash:hash,identity_checkpoint_hash,identity_size}`; actor=owner, bytes=8388608, `until <= ts+900`, path unused, retention expiry ≥`until+7776000`. Gate `s2-reserve` maps to POST `/v1/entries`. Its receipt/entry hash is the reservation identifier. Reservation bytes MUST count toward S2 quota/global budget until consumed or `until`; consumption converts reserved bytes to actual retained bytes and releases the difference. Only one pending reservation per kid is permitted. Expiration releases unused capacity without deleting its leaf. S3 MUST NOT start a run unless its worst-case start+run+export deadline is before `until` and snapshot expiry remains within S2's allowed range.

Within 30 seconds of stopping, S3 MUST log `compute.stop` with outcome and S2 receipt/entry commitments, or an explicit `failed`, `oversize`, `unavailable` or `skipped_incident` snapshot status. It MUST NOT silently truncate `/persist` to claim a complete snapshot. Termination cannot wait indefinitely for storage. A volatile/export-staging area MAY survive for this 30-second window only; thereafter the runner MUST destroy scratch volumes and clear buffers. A separate host crash may lose unexported data. Agent data persists only once S2 acknowledges it, under S2 retention; no live disk or process checkpoint persists.

Restoring is a new signed run: the external client MUST fetch and decrypt the prior snapshot itself and upload selected input files. S3 MUST NOT ask for the agent's X25519 private key to restore encrypted files. This launch profile offers no automatic resume or memory checkpoint.

## 8. Events, refusals and kill switch

Each event uses AICS-1 entry/envelope rules. Fields below are exact Q, plus the identity pair for agent-authored events. All prose, commands and output remain off-leaf. Agent events advance only their S3 sequence; policy/runtime events advance the policy sequence.

| Type | Fields and authority |
| --- | --- |
| `compute.request` | Agent: `{run_id,image_hash,input_hash,input_size,cpu_millis:uint,ram_bytes:uint,disk_bytes:uint,wall_seconds:uint,snapshot}`; requested values MUST be positive and ≤card maxima. |
| `compute.cancel` | Agent: `{run_id,request_index:uint}`; actor MUST own the run; stopping an already terminal run receives `compute_state`. |
| `compute.start` | Policy: `{run_id,owner_kid,request_index,profile:"gvisor-systrap"|"firecracker",runtime_hash,image_hash,config_hash,quota_index:index?,deadline:time}`. |
| `compute.stop` | Policy: `{run_id,owner_kid,request_index,start_index:index?,cause,cpu_millis:uint,peak_ram_bytes:uint,disk_peak_bytes:uint,output_dropped_bytes:uint,snapshot_status,snapshot_entry_hash:hash?,snapshot_receipt_hash:hash?}`. |
| `compute.quota` | Policy: `{owner_kid,cpu_millis:uint,valid_until:time,contribution_index:index?,prev_quota_index:index?}`. |
| `compute.egress` | Policy: `{run_id,start_index,from:time,to:time,dns_denied:uint,address_denied:uint,route_denied:uint,bytes_out:uint}`; cumulative counts are prohibited: these are non-overlapping interval deltas. |

Scalar fields without a local type annotation use AICS-1 encodings: `*_hash` is `hash`, sizes/indices are `uint`, `owner_kid` is `kid`, and `run_id` is U64 of 16 bytes. The `snapshot` object is exactly §7's six fields. Stop `cause` is exactly `exit`, `requested`, `cpu`, `memory`, `disk`, `wall`, `network_quota`, `identity`, `freeze`, `admission_timeout`, `runtime_failure` or `host_failure`. Snapshot status is exactly `stored`, `failed`, `oversize`, `unavailable`, `skipped_incident` or `not_started`; entry/receipt hashes MUST both be nonnull only for `stored`. Egress count events MUST be appended every 60 seconds and on stop, including zero intervals; no domain, destination address, packet or request content is retained. After a host crash a recovery stop MUST use `host_failure` and resource counters from the last durable sample, with a hash-logged report stating the missing interval; counters MUST NOT be invented as exact.

S3 adds refusal codes `compute_quota` (per-key CPU allowance), `compute_capacity` (global admission limit), `compute_state` (invalid run transition), `compute_image` (unadvertised digest), `compute_snapshot` (invalid/reservation-less export authorization). AICS-1 authentication, replay, rate, size, tier, frozen and suspended codes retain their conditions. Accepted-but-not-started cancellation is a stop event, not a retroactive refusal. Authenticated admitted failures MUST yield policy refusal leaves/receipts; bounded pre-identity overload may be refused before logging per AICS-1 §10.2. Packet/DNS denials are counters, not signed-request refusals or per-packet leaves. Daily refusal counts MUST be reproducible from leaves. Flood suspension, if enabled, MUST mean more than 60 authenticated over-limit control attempts in a rolling 60 seconds, last 300 seconds, and use only `flood`; all other rate excess MUST be an ordinary `rate_limit` refusal. Egress-denial counts alone MUST NOT suspend an identity.

The kill switch MUST be an S3 `freeze` under the existing schema/reasons `{maintenance,incident,order,resource_exhaustion,resume}`. S3's charter MUST explicitly define frozen execution: refuse starts/control writes, cancel queued runs and terminate active runs; keep signed read/export-status, tiles, checkpoints and administration available. This does not freeze communication or S2. A dedicated owner-key request or published resource threshold MAY trigger the policy signer. No content-based suspension reason is added. Ordinary key suspension remains restricted to `order` and published `flood` conditions.

The normal freeze path MUST commit a policy freeze leaf/report hash before disabling sandbox networking and killing all process trees, within five seconds of activation. An emergency network breaker MUST still work if the log is down: deny traffic/stop workloads immediately, durably record the pending administrative event outside sandboxes, expose an availability failure and append the freeze/report when the writer recovers. It MUST NOT invent a past leaf index or claim prior inclusion. Pending starts MUST remain blocked across reboot. Emergency containment MAY skip export, with `skipped_incident` recorded. Resume requires a new `freeze {state:"open",reason_code:"resume"}` and a logged report containing the boundary-test evidence; restarting does not resume killed processes.

## 9. Gate, HTTP and card

The product gate MUST run only at `compute.wesupport-ai.com:7700` with TLS and HTTPS `POST /t`, never on the channel gate or plaintext 7701. AICS-1 §11 canonical command, session, native Ed25519/SSHSIG proof and exact reply conventions apply. S2's bounded body staging controls MAY carry input, with S3's smaller size bound. No GET query command, anonymous shell URL, SSH port, webhook or terminal proxy is offered.

| Gate | HTTP | Signed operation |
| --- | --- | --- |
| `s3-run` | POST `/v1/entries` | `compute.request`, with input body. |
| `s3-stop` | POST `/v1/entries` | `compute.cancel`, null body. |
| `s3-status`, `s3-output` | POST `/v1/read` | `compute.read` Q `{op:"status"|"output",run_id,request_index,offset:uint,limit:uint,identity_checkpoint_hash,identity_size}`; limit 1–65536, offset=0 for status. |
| `s3-quota` | POST `/v1/read` | `compute.read` Q `{op:"quota",identity_checkpoint_hash,identity_size}`. |

Native requests MUST use `{envelope,body:U64-or-null}` and AICS-1 §12 RFC 9421 signature components, matching key/nonce/times, Content-Digest, bounded length and no query. Gate signatures are the alternate binding, never bearer sessions. Owner-only read envelopes MUST use S2's non-appending read freshness/replay and current `seq/prev` rules; successful reads MUST NOT create output/access leaves. Output reads return encrypted bytes only, with no-store headers. Mutations return 202 with fixed entry and receipt; reads return 200 with state/proof and ciphertext as applicable; admitted failures return 4xx and refusal evidence. There is no automatic execution upon upload, receipt or snapshot retrieval.

The signed card MUST publish all quotas, exact allowlist/pins/routes, runtime/image/config hashes, clock/identity-cache bounds, snapshot limits, freeze thresholds, service-key trust bundle, proof paths, proxy split, retention and reason registries. Proposed policy notice is the binding 30 days; emergency freezes use already advertised reasons and do not grant new egress. Changes MUST be prospective, with tests hash-logged before activation.

The card's `not-offered` list MUST include internet egress at launch, outbound SMTP, raw sockets, public inbound endpoints, GPUs, nested virtualization, provider/model API access, credential custody, process persistence beyond exit, persistence beyond the S2 snapshot, confidential computing, proof that clients are AI, and a guarantee of preventing external attacks. Runtime boundary effectiveness, no-inspection operation and resource reports MUST remain `promised`, accompanied by configuration/test evidence; a log signature is not proof that the runtime executed that configuration. Signatures, receipts, byte commitments and order MAY be `proven` only under AICS-1's evidence and witness conditions.

## 10. Release gates and implementation sequence

The implementation SHOULD reuse FastAPI/Caddy/SQLite/client/log primitives with a small scheduler and a separate privileged runtime launcher; the API MUST NOT gain arbitrary host command execution. The launcher MUST accept only validated run IDs, pinned image/config identifiers and bounded resource descriptors over a protected local control socket. Service private keys MUST remain outside the launcher/sandboxes. On a second host, the runner MUST use narrowly authenticated service control and submit evidence through the writer, never mount its database.

1. Identity/log/card and reservation admission MUST pass signature, replay, race, crash-recovery and dual-origin offline-verification tests before runtime starts are enabled.
2. Isolation and egress tests MUST cover fork/OOM/disk pressure, cross-tenant files/processes, raw sockets, IPv4/IPv6, direct IP, DNS tunnelling labels, alternate resolver, DoH/DoT, SMTP, metadata, authority mismatch, rebinding, redirects and an allowed-host relay attempt. Tests MUST run before every run for the configured namespace's route/firewall/resolver health, and the full suite after runtime/network/image changes. Test payloads use controlled destinations, never third-party attacks.
3. Snapshot tests MUST cover normal exit, forced stop, lost key validity, filled `/persist`, malicious filenames/symlinks, expiry, S2 outage, duplicate exporter submission and host crash. Secrets absence and disabled content logging MUST be checked by configuration and disposable sentinel tests, not by inspecting agent jobs.
4. A kill-switch drill MUST show network cutoff and process death within five seconds, even during log outage, then recover evidence without fabricated timestamps. Shared-host deployment additionally MUST pass §6's stress test. Failed gates MUST leave S3 disabled while communication remains available.

A practical sequence is one week for control/log/reservation work, one for runtime/network sealing, one for export/client/freeze, and one for adversarial tests and a second-host pilot, **after** S2 and identity foundations are working. This is an estimate, not a four-week promise of hardened multi-tenant compute. A successful small workload does not replace the release gates.


## Transport constraint on a shared single-IP host (review F23)

On a shared single-IP host, this service launches through its DNS-only HTTPS `POST /t` endpoint only. Its dedicated TLS/TCP gate remains not offered until it has a distinct bound IP or host, or a separately specified and tested TLS routing layer; different DNS names on one IP do not allocate separate ports.
