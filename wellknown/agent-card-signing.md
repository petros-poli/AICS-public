# Discovery card signing at build time

Sources checked 2026-10-18: [A2A 1.0 AgentCard and §8.4](https://a2a-protocol.org/latest/specification/), [pinned 1.0 specification](https://a2a-protocol.org/v1.0.0/specification/#84-agent-card-signing), and local `docs/spec/AICS-1.md` §§6.4, 13.

The checked-in card is unsigned. Do not insert example keys or signatures. It is a discovery draft with the required AgentCard field shapes, not a conformant A2A endpoint declaration: `supportedInterfaces` is empty. A2A §8.3 requires an actual interface. Native AICS routes do not implement A2A operations; do not label them JSONRPC or HTTP+JSON. Before claiming A2A conformance, implement and test a binding, then supply its URL, protocolBinding and protocolVersion (A2A version, not AICS version). This implementation is outside this static-file package.

The top-level `url` is a requested local compatibility field, absent from the 1.0 AgentCard schema. Strict A2A consumers may reject or discard it; an interoperable signed A2A card must move that URL to the real supportedInterfaces entry and remove the extra field. Authentication is described in prose because A2A's security-scheme union has no RFC 9421 variant. Do not misrepresent Signature-Input/Signature as bearer, API-key or Authorization credentials. Agree a documented A2A authentication extension/profile before publishing a fully interoperable card. The unsigned draft does not promise an anonymous API.

Build procedure after resolving those compatibility blockers:

1. Finalize all content and verify deployed skills, especially swarms. Load the policy signing key from the build secret store; never commit it. Use the policy_kid from the independently pinned AICS trust bundle. Keep log, policy and owner keys separate.
2. Remove `signatures`. Apply A2A §5.7 and §8.4.1 field-presence rules recursively: keep required fields and explicitly present optional fields, including false capability booleans; omit default-valued non-presence fields and optional empty repeated fields. Do not blindly delete every false, zero or empty value. Canonicalize with an RFC 8785 JCS implementation, not ordinary sorted JSON.
3. Let U64 be unpadded base64url and J be UTF-8 JCS bytes. Set `protected = U64(J({"alg":"EdDSA","kid":policy_kid,"typ":"JOSE"}))`. Compute `payload = J(normalized_unsigned_card)` and sign `ASCII(protected + "." + U64(payload))` with Ed25519. This signs the encoded JWS payload, not a payload hash or an AICS envelope digest.
4. Add `signatures: [{"protected": protected, "signature": U64(signature_bytes)}]`. The payload is reconstructed from the card, not stored in the signature entry. For this instance permit no unprotected header, embedded key, jku, b64=false or algorithm substitution. Verify the emitted artifact with an independent verifier and the pinned policy public key before publishing; any content change requires signing again.
5. Verification removes signatures, repeats the exact presence normalization and JCS, enforces the protected header policy, and checks Ed25519. Keys obtained solely from this card/API do not establish trust. Reject revoked keys or trust-bundle disagreements.

The AICS assurance card at `/.well-known/aics-card.json` is a separate artifact generated elsewhere. AICS-1 §13 removes only signatures before signing: all its required false/zero/null/empty values remain. Hash the FULL signed assurance card's JCS bytes with SHA-256 for its `policy/kind=card` document_hash. The first such hash is bootstrap_card_hash; it is not the discovery card hash. Publish identical JCS trust-bundle bytes `{v:1,origin,log_vkey,policy_kid,owner_kid,bootstrap_card_hash}` via `_aics.wesupport-ai.com` TXT (`aics1=` plus U64), the PyPI AICS_TRUST_BUNDLE constant and public repository README (bytes plus digest). Trust must be pinned or independently accepted; three founder-controlled locations are distribution diversity, not independent authorities. Later card changes follow logged activation and the 30-day notice period.
